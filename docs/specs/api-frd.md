# Platform API (`api/` — REST + Postgres) — FRD

Status: **Signed 2026-09-05 (William)** · Surface: Platform (merchant-facing REST, internal ingest, dashboard backend) · Sources: detailed doc §2, §3 Objects, §4.2 frozen SDK surface, §4.4, §5.1–5.3, §6 item 7 & 9, §8, §9 Architecture, §12 Week 2/4, §15; `api/README.md`; `.env.example`; checkout FRD (Data block, BR-CHK-005); dashboard FRD outline; design brief §3.

## Problem

Merchants must integrate "in an afternoon" with the nouns they already know from Stripe (doc §2, §3). The API is the only thing the SDK, the hosted Checkout, the dashboard and the docs talk to. It owns the truth about Merchants, Products, Customers, Checkout sessions, Subscriptions, Invoices/Settlements, Webhook endpoints, Events and Deliveries; it turns indexed chain events into merchant Events; and it must serve exactly the frozen §4.2 surface — "anything not listed does not exist" (§15).

## User stories

1. As a Merchant engineer, I want `products.create` and `checkout.sessions.create` with my secret key and get back `session.url`, so that the quickstart takes under 10 minutes (§6).
2. As a Merchant engineer, I want `GET /v1/subscriptions/:id` with `rate` and `started_at`, so that I can compute a live meter locally without per-second webhooks (§5.1).
3. As a Merchant, I want separate test and live keys, hashed at rest and shown once, so that a leaked database does not leak my keys (§9).
4. As the hosted Checkout, I want to load a session with only a publishable key and a session id, so that the secret key never reaches the browser (BR-CHK-005).
5. As the indexer, I want an ingest endpoint that accepts the same chain event twice without side effects, so that Envio preload double-fires are harmless (§15).
6. As a demo presenter, I want test clocks in test mode, so that the video shows an hour of accrual in seconds (§6 item 9).
7. As a judge, I want a published OpenAPI document that matches the SDK, so that the docs are not a lie (§6 item 7, §15).

## Open

- ~~`checkout.session.completed` timing~~ **Decided 2026-09-05 (William):** fires on `StreamStarted`, i.e. when the stream is running on chain. Under the permit design signing, escrow and start are one transaction, so there is no earlier meaningful moment; provisioning access on a signature the chain might reject is what Stripe also refuses to do.
- Ordering of the cap-end pair: `invoice.payment_failed` before `subscription.canceled` (FR-API-071) is a convenience only — deliveries carry no ordering guarantee (worker BR-WRK-004), so the docs must tell merchants to key on `evt_` id and read `data.object.status` rather than rely on arrival order.
- Merchant `payout_address` is the `merchant` argument to `StreamFactory.create`; changing it after streams exist only affects new streams — document.
- ~~Whether Customers and Invoices endpoints are dashboard-visible~~ **Yes** — both pages are built in the dashboard (FR-DSH-050s, FR-DSH-060s) and read these endpoints through the shared auth middleware (FR-API-102).
